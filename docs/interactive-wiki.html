Visit Heatmap — how it works

Every position a tracked device has visited is drawn on a map with an opacity proportional to recency: today is solid, each day it fades, and once a visit is older than a configurable horizon it disappears. A small companion integration records the positions durably; a custom card reuses the stock ha-map and injects the fading visit layer.

Click any box in a flow diagram to see what it does. Open any ▸ code block for the real source. Scroll through — each section links to the next.

01Overview — ten-second tour

The integration records; the card paints. The two halves never talk directly — they meet only over a Home Assistant WebSocket message and a JSON file on disk.

Capture

Every GPS device_tracker.* state change fires EVENT_STATE_CHANGED. The integration keeps a debounced subscriber that turns the event's latitude / longitude / last_updated into a fix — the raw unit of truth.

See §05 Capturing a fix.

Record

Each fix is classified (moving or stationary) and either added as a new row or used to refresh an existing one within the dedupe radius — so revisiting a place never piles up duplicate dots. Rows persist to visit-heatmap.json via debounced atomic writes.

See §07 and §08.

Read

The card asks for rows with the visit_heatmap/points WebSocket command filtered to the entities it draws.

See §09 Backfill & the read API and §13.

Paint

The card turns each row into a Leaflet.circleMarker whose fill opacity is the day-fractioning decay of its last visit, injects those into a stock <ha-map>/ layers property — no reimplementation of Leaflet needed.

See §13 and §15.

02The ground truth: one fix end-to-end

This is the whole journey of a single position update. Click each stage. The env badges tell you which process owns the stage.

1 · A tracker updates

HA core — outside this repo

A tracker integration (companion app, OwnTracks, GPSLogger, GoogleFindMy-HA, …) publishes a new state for e.g. device_tracker.phone.

This project is deliberately agnostic: it consumes any tracker whose state carries latitude/longitude attributes.

2 — The bus delivers STATE_CHANGED

core/bus.py

HA dispatches EVENT_STATE_CHANGED to every subscriber. We queue-audited one at __init__.py.

3 — Runtime filters & classifies

__init__.py

_on_state_changed accepts only device_tracker.* entities with GPS attributes, computes speed against the previous fix, and decides moving or stationary. See §06.

4 — add_fix: dedupe or add

logic.py

The pure function checks every existing row for the same device within dedupe_radius (default 100 m). A hit refreshes last_seen; a miss adds a row. Identical timestamps are a no-op duplicate. See §07.

5 — Debounced durable save

store.py

Mutations schedule a save (debounced 2 s, cancellable so bursts collapse into one). save() writes a temp file then os.replace — atomic, crash-safe.

6 — Card fetches

websocket.py → visit-heatmap-card.js

The card sends visit_heatmap/points with its entity list. The command runs store.query and returns JSON-safe rows (retention-filtered only — never the card's visual horizon).

7 — Layers are painted

visit-heatmap-card.js

_buildLayers creates a circleMarker per compatible residence point with opacity from the decay model, and dashed polylines between moving fixes. The stack of layers is passed to <ha-map .layers>.

03Two halves, one HACS repo

⚙️ custom_components/visit_heatmap/
The "recording" half — a Home Assistant integration that stores visits durably. Only new HA, pure, unit-tested.
🗺️ www_src/visit-heatmap-card.js
The "painting" half — a LitElement card cloned from HA's own map card core, blending the visit layer into the native map element.

They communicate across a single seam: the WebSocket command visit_heatmap/points. Keeping recording and rendering in one repo means the card and integration ship and version together for this user, while the seam keeps them individually replacable.

04Integration lifecycle

Home Assistant loads a config-entity-domain integration like this:

  1. async_setup runs once per domain lifetime — it registers the WebSocket command (so options-flow reloads can't double-register).
  2. async_setup_entry builds a single VisitHeatmapRuntime, starts the store, subscribes to EVENT_STATE_CHANGED, registers the frontend resource, and attaches the update listener.
  3. Changing options triggers async_reload_entry: unload then re-setup — fresh store, same command.
  4. async_unload_entry tears down: unsub bus listener, cancel save+backfill tasks, flush any pending rows to disk.

06Moving vs stationary

    
The design (ADR-0002) separates places you stayed from how you got there.
    The classifier is a one-liner made of three pure functions:

    

    

      

        
Step by step

        
speed_between(prev, current) divides great-circle
        distance (haversine_m) by wall-clock delta
        current.timestamp − prev.timestamp. The first fix of a
        device has no previous fix → speed is None.

        
classify_moving(speed, threshold) returns
        False when speed is None
        (first fix counts as a stay), else speed >= threshold
        with default threshold 2 m/s.

      

    

    

      ▸ logic.py — haversine, speed_between, classify_moving
      

    


    
Decision grid

    

      
Situationspeedmoving?Rendered as

      
First fix for a deviceNonestationarysolid dot (home).

      
Repeated staying-motion < threshold< 2 m/sstationarythe residence's dot.

      
Walking/car/train, w thick clicks >= threshold>= 2 m/smovingsmall faint dots + dotted journey lines.

    

  


  

    
07Dedupe & refresh

    
A phone records a position every few minutes. Without dedupe, an evening at home
    spawns dozens of overlapping dots. add_fix solves this: a
    new fix within the dedupe radius of a device's existing rows refreshes the existing
    row's last_seen (and its moving flag) instead of appending.
    first_seen never changes — so the dot's start of a
    stay stays put.

    

    

      

        
added
logic.py add_fix
        
No row for this device within dedupe_radius → a new row
        with first_seen = last_seen = fix.timestamp. Always schedules a save.
        New-dot appears.

      

      

        
refreshed
logic.py add_fix
        
A row for this device exists within the radius → its last_seen
        advances to the fix's timestamp (first_seen untouched; the
        moving flag flips to the new fix's classification). The card re-derives the dot's
        opacity from the later last-seen, so a re-visited place stays solid — no pile-up.

      

      

        
duplicate
logic.py add_fix
        
An exact equal timestamp for that device (rare, e.g. recorder re-delivery) — nothing
          changes, no save scheduled.

      

    

    

      ▸ logic.py — add_fix (the whole classify+dedupe decision)
      

    

    
When backfill replays recorder history it feeds the same
      add_fix, so backfilled rows are indistinguishable from
      live ones (see §09).

  


  

    
08Storage & rotation

    
Rows live in memory and are mirrored to
      visit-heatmap.json next to HA's config. The JSON encode/decode
      keeps datetime objects on the Python side; the file stores
      ISO strings with a trailing Z.

    

      
{
  "version": 1,
  "rows": [
    {
      "device": "device_tracker.phone",
      "lat": 51.5074, "lon": -0.1278,
      "first_seen": "2026-08-06T18:12:03.400000Z",
      "last_seen":  "2026-08-06T18:12:03.400000Z",
      "moving": false
    }
  ]
}

    

    
    
      
  • Atomic — writes to a temp file in the same dir then
      os.replace; never a torn file.
    • 
      
  • Debounced — a 2 s trailing debounce collapses bursts of many fixes
      into one disk write (see §05).
    • 
      
  • Rotation — purge(retention_days) drops rows
      with last_seen older than the retention (default 90 days).
      This is a capacity limit, independent of the card's cosmetic horizon.
    • 
      
  • Rebuild — on start, rebuild_last_fixes re-seeds
      the per-device previous fix from the most recent stored row, so classification
      survives HA restarts.
    • 
    

    

      ▸ store.py — save & load & query
      

    

  


  

    
09Backfill — importing the past …and the read API

    
On first install the store is empty, so the map would be blank until devices move.
    async_backfill pulls up to backfill_days
    (default 10) of recorder history via
    history.state_changes_during_period and replays each
    state through the regular add_fix pipeline. The shared slot record
    is debounced like live data.

13Rendering the visit layer

    

    

      

        
_buildLayers

        
Stationary rows → one circleMarker (radius 6)
        with stroke+fill colored per device; fillOpacity = _opacity(row).
        Moving rows → tiny dashed markers (radius 3) grouped per-device; their
        _buildPaths…

      

      

        
zones & tooltips

        
Points inside a configured Home Assistant zone can be hidden
          (exclude_zones); hovering a dot shows a tooltip with
          device, last time, and zone name. No reverse geocoding in v1 (ADR-0004).

      

      

        
injection into ha-map

        
The constructed array of Leaflet layers is bound to the stock
        <ha-map>'s public layers
        property via Lit. Leaflet is no longer bundled with the card: it is resolved at
        runtime from the ha-map element (el.Leaflet, retried until
        it mounts) and every layer is built with that exact copy — the card never mixes two
        independent Leaflet copies, which would corrupt the shared SVG renderer's
        _empty bookkeeping and crash on map moves.

        
A _verifyLayersInjected guard periodically
        checks map.hasLayer(layer) and warns if any layer was
        dropped.

      

      

        
trails

        
For config parity with the default map card, it also subscribes to
        history/stream when hours_to_show
        is set, drawing a semi-transparent trail of recent movement (the stock card's feature,
        reused).

      

    

    

      ▸ card — _buildLayers (the meat)
      

    

  


  

    
14Journey lines — joining the dots

    
Moving rows for one device are sorted by time. A dashed polyline joins consecutive
      dots unless a segment should break:

    
    
      
  • time gap — the delta exceeds max_gap (default 30 min) and
      the dots are farther apart than max_dist (default 1000 m);
    • 
      
  • long stationary between — a stationary row that lasted at least max_gap
      lies between the two fixes (a real stop splits the trip; a brief pause stays inside one journey);
    • 
      
  • too old — either endpoint's opacity hit 0.
    • 
    

    
A surviving segment gets the decay opacity of its more-recent endpoint —
      a journey you just took is solid, a trip from last week is faint.

    

      ▸ card — journey segmentation & opacity
      

    

  


  

    
15The decay model

    
Opacity is a continuous exponential fade:

    

      
opacity = (1 − decay_rate)age_days

      
age_days measured from last_seen to now; floored at 0.0.

    

    
The card and the backend both implement this (_opacity in JS,
      decay_opacity in logic.py — the server
      value exists only so the pytest can mirror the client contract). The two knobs:
      decay_rate = the fractional decline per day (default
      0.1 → 10%/day), and horizon = a visit vanishes once
      age_days > horizon (default 30). Both are card-side only; they never touch the store.

18Testing & CI

    

      
pytest — 22 tests
Pure logic.py/store.py unit tests; the whole homeassistant layer is only in the live HA run. Runs in CI after ruff.

      
ruff
Python lint gate (custom_components/visit_heatmap).

      
esbuild → www/…card.js
Builds the bundled, minified card the card resource loads; then node --check validates the emitted bundle.

    

    

      
Why no tsc? The card is deliberately plain JS (the card is ES classes
        built with esbuild). CI "type-check" is therefore the build + a syntax check of the
        emitted file — documented against ticket 08. There is no browser test harness for the
        card; verify by eye on a live instance.

    

  


  

    
19Glossary

    

      
TermMeaning

      
fixA single GPS observation with device, lat/lon, timestamp.

      
rowA deduplicated place in the store: one dot on the map.

      
stationaryA fix that is not classified "moving" — a stay place.

      
movingA fix whose speed/delta ≥ threshold; rendered small + joined into journeys.

      
first_seen / last_seenRow bookends; first_seen only set once, last_seen advances on refresh.

      
dedupe_radiusWhen a new fix lands within this distance, refresh the row.

      
decay_rate / horizonCard knobs: %-per-day fade factor, and the age after which a visit disappears.

      
retention_daysServer-side pruning age; capacity bound, not cosmetic.

      
max_gapLongest time between two moving fixes that can be connected by a journey.

      
max_distMoving fixes closer than this (m) stay connected even past max_gap.
